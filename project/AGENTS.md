## 2. 开始工作前

1. 阅读与任务有关的 `README`、现有规范、配置、测试及代码；需要背景材料时检查 `doc/contexts/`。
2. 若存在 `lessons/`，阅读与当前任务相关的经验记录，不要求通读无关内容。
3. 明确任务范围、已知事实、关键假设、待确认事项和验收方式。只有缺失信息会实质影响正确性或方案选择时，才优先向用户澄清。
4. 任务包含三个及以上实质步骤，或涉及架构决策时，先形成执行计划，覆盖实施与验证；简单任务可直接执行。
5. 使用子代理的前提是当前工具支持且任务可独立拆分；不因规则要求而人为增加代理。

执行过程中若发现关键前提错误、测试结论相反或影响范围明显扩大，应重新评估方案，必要时再向用户确认。

## 3. 项目目录与文档归档

非代码工程引用的 Markdown、HTML、PPTX 等文档，默认采用以下目录结构：

```text
doc/
├── contexts/          # 用户提供的上下文材料；仅用户可写
├── artifacts/         # 正式报告、方案、汇报等交付物
├── investigations/    # 调查、技术分析、Bug 分析等文档
└── assets/            # 正式交付物使用的图片、SVG 等素材
```

- **禁止写入 `doc/contexts/`**；只可读取用户放入的材料。
- 正式对外文档放入 `doc/artifacts/`；调查分析文档默认放入 `doc/investigations/`；配套素材放入 `doc/assets/`。
- 只有在实际需要落盘文档时才创建缺失的目录；不为简单问答或纯代码修改生成无关文档。
- 如果仓库已有明确且有效的目录规范，优先沿用，不擅自建立平行目录体系。
- 本节不适用于工程源码及其必需的配置、内嵌文档，后者遵循所属模块的现有组织方式。

## 4. 设计任务

### 4.1 交付要求

正式设计文档应面向不熟悉本项目实施过程的读者，能够独立阅读，不采用对话记录或工作日志的写法。按任务适用性包含：

1. 背景、目标与非目标。
2. 已知事实及证据来源、假设、待确认事项。
3. 需求、约束和验收标准。
4. 备选方案及关键取舍。
5. 推荐方案与决策依据。
6. 主要风险、验证方式和实施步骤。

无需为不适用的章节填充空话。没有实际调研、访谈、测试或测量结果时，严禁编造；估算值必须标注为「预估」并说明依据。

### 4.2 方案对比

- 存在真实的架构或技术选型时，原则上比较 **2～3 个可行方案**；若客观上只有一个合理方案，应说明限制条件，而不是凑数。
- 每个方案说明适用条件、优势、主要风险及不推荐它的理由；对最终推荐方案也要陈述反方论证。
- 优先使用第一性原理分析需求与约束，控制复杂度、维护成本及变更范围。
- 验收条件使用可验证的 checklist 或 Given/When/Then；不可验证的愿景表述不作为验收条件。

## 5. 代码开发与 Bug 修复

- 修改前定位相关实现、依赖、调用方和现有测试，明确预期行为及兼容性要求。
- Bug 修复优先通过日志、错误信息、复现步骤与失败测试定位根因；避免以掩盖症状的临时补丁替代修复。
- 在确保正确性、可维护性及兼容性的前提下执行最小必要修改，不做无关重构。
- 优先补充或更新能够覆盖问题的测试；运行与改动范围相匹配的测试、检查或构建，并如实报告结果。不能运行的验证项目说明原因。
- 涉及破坏性数据操作、公开接口的不兼容变更或重大架构取舍时，先取得用户确认。
- 类、函数在用途或输入输出不够直观时添加中文注释；复杂逻辑在关键步骤补充必要说明，避免重复代码含义的注释。
- 用户修正暴露可复用的错误模式时，可记录到 `lessons/`；不为一次性措辞修改或微小调整强制创建记录。

## 7. Markdown 与交付物格式

- 文档使用 Markdown；需要表达流程或关系时使用 Mermaid，需要表达结构化数据时使用 YAML/JSON。
- Mermaid 中包含空格、特殊字符，或可能与语法冲突的节点/边标签，应使用符合 Mermaid 语法的引号；以实际渲染和语法检查结果为准。
- 输出正式交付物时只保留其目标状态，不在文件中附加修改历史、对话过程、版本前后对比；用户明确要求时除外。
- 遵循项目现有模板与命名规范。无现成模板时使用简洁、层级清楚、来源可追踪的结构。

## 8. 完成验收

交付前逐项确认：

- [ ] 交付内容覆盖用户明确要求，且未擅自扩大范围。
- [ ] 事实、推测和假设已区分；数据与外部结论具有来源或明确标注限制。
- [ ] 代码改动已做相应验证；未通过或未执行的验证已如实说明。
- [ ] 不兼容变化、主要风险及待确认项已明确列出（如适用）。
- [ ] 文档与附属资源位于约定目录，未写入 `doc/contexts/`。
- [ ] 交付文件没有无关变更记录、冗余内容或不必要的产物。

**完成判定**：只有满足适用的验收项，才能宣称工作已完成。未完成项必须明确说明，不能将计划执行等同于已验证结果。
