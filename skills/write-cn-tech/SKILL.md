# 中文技术文档写作与审核

帮助目标读者沿正文理解问题、概念、推理和结论。默认在同一任务中完成“写作 → 审核 → 修订 → 复核”，发现问题后直接修复。用户明确只要初稿或只审核时，按指定阶段交付。

适用于根据对话、资料、调研、分析、方案或代码生成的中文技术文档，不预设依赖代码仓库。遵守用户指定的读者、范围、格式、篇幅与已有约定；文件生成、网页实现及特定格式处理配合相应工具。

## 文风与篇章优先级

采用清晰、克制、连贯的专业分析文风。借鉴 ASD-STE100 的明确指代、统一术语和减少歧义原则，不机械套用句长、词汇或句式限制。篇章连贯优先于单句简化；复杂句能准确表达因果、条件、对比和限定关系时保留，不为流畅删掉事实、细节或推理。

技术报告保持“宏观结构清晰、微观论述连贯；技术信息结构化，分析与推理段落化”。背景、原理、设计依据、取舍和结果分析用段落展开；需求、约束、参数、接口、验证条件和操作步骤按检索、比较或执行需要使用条目、表格、公式和图示。图表附近仍须解释影响判断的关系和条件。

形式服从用途：研究分析以段落论证为主，规范与操作规程可用条目，工程设计兼顾决策依据和信息检索。同一文档按小节功能选择形式，不规定段落比例或固定目录，不把完整分析拆成孤立短句和项目符号。

## 1. 明确读者与任务

从请求、材料和已确认上下文提取以下信息，内部记录即可：

- **读者**：已有知识，以及不能默认掌握的专门概念。
- **文档受众对象**：谁将阅读或使用文档，其职责、关注点与文档的关系；区分已确认的实际受众与为审核设定的模拟角色。
- **任务**：读完要能解释、判断、决策或完成什么；核心问题是什么，预期受众采取什么行动（如适用）。
- **关键关切**：完成该任务必须了解的依据、前提、取舍、风险及限制；不预设每篇文档都需要审批或实施。
- **用途与范围**：研究分析、设计决策、规范还是操作；所需深度、篇幅、格式及保留要求。
- **证据**：已核实事实、分析推断、待验证假设与示例分别有哪些。

读者未指定时，默认“具备一般技术背景，但未接触本文专门概念”。文档受众对象的具体职责不明时，可按文档用途选择模拟审读角色，但不得宣称这是已确认的实际受众。若不同假设会明显改变路线、深度或核心判断，按第 4 节确认；否则说明必要假设后继续，不默认技术读者认识所有术语。

改写已有文档先读全文，保留用户要求的结构、结论、术语与标识符。只有片段时限定审核范围，不宣称全文通过。

## 2. 建立概念依赖与整体认识

先识别理解核心问题必需的概念，再安排章节。“理解 B 需要 A”是知识依赖，不等同于系统的执行顺序或一般关联。长文可记录概念的通俗解释、前置知识、首次解释位置、后续用途和固定名称；简单任务不必制作工作表。

- 区分读者已知与本文必须解释的概念。已知须有读者设定支持，熟悉的基础知识不重复讲解。
- 按依赖顺序引入；定义本身不得依赖尚未解释的关键术语。循环依赖先用日常语言或最小实例建立共同直觉，再精确定义。
- 首次实质使用时，通过当前问题或例子说明概念是什么、为什么需要、在此处有什么作用。只展开英文全称不算解释；不机械堆砌定义。
- 首次展开一组对象或分类时，先建立整体认识：划分什么、依据是什么、与前文是什么关系，再展开组成、属性或职责。不同分类维度不能因并排列出就被误写成互斥类别。
- 删除不服务于核心问题的概念，深入细节可移至附录。正文理解所需的解释不能依赖附录或文末术语表。

标题、图注、表格和代码前的说明也属于首次接触位置。摘要或总览可提前给结论，但应使用通俗表达或简短解释。导语、表格与例子的先后服从读者理解，不要求所有定义先于表格，也不固定让表格承担首次介绍。

## 3. 建立主线与章节承接

从读者的认知过程组织内容，不把代码模块、类、函数或知识点分类直接当作目录。只有这些排列符合理解顺序时才采用。“故事性”指问题逐步回答、前提逐步积累、结论自然推出，不添加虚构场景、悬念或文学铺陈。

可先整理一条问题链：

> 遇到什么问题 → 现有做法为何不足 → 需要哪些概念 → 方法如何工作 → 有何依据与代价 → 在什么条件下怎样选择。

按用途调整路线：原理讲解由问题进入机制与实例；调研围绕研究问题综合证据；方案比较先确定约束与评价口径；操作说明明确目标、前提、步骤与结果检查。对需要支持选择、评审、验证或执行的文档，确保重要结论与必要依据、适用条件、取舍或风险、后续行动之间有可追踪的联系；不向纯解释型文档强加成本、审批或落地计划。不要求每篇包含所有环节，问题链也不直接充当标题。

每个主要小节应能回答：它解决什么问题、承接前文什么结论、为后文建立什么基础。答不出的内容应合并、重排、删除或移至附录。用因果、递进、对比、条件、实例或证据关系衔接，不只靠“接下来”“此外”“综上”；并列章节先交代共同问题和比较口径。

安排章节时同步判断是否需要图表说明边界、角色、分支、状态、对象关系、数据去向或调用顺序。复杂关系主动配图，放在相关论述附近，不在末尾集中补图；具体规则见第 5 节。

## 4. 按影响决定是否确认

先形成具体、可评估的方案，再合并提出少量必要问题，通常不超过三个。以下选择无法从上下文或既有授权确定时，先确认再写依赖它的正文：

- 读者或用途不明确，不同选择会明显改变解释、深度或路线。
- 有两条实质不同的叙事路线，无法判断哪条符合目标。
- 需要明显改变范围，或重构用户明确要求保留的结构、术语或结论。
- 资料对关键结论存在分歧，需要确定评价标准或是否呈现分歧；先核实事实，不能让用户偏好替代事实判断。
- 用户明确要求写作前确认概念关系、提纲或主线。

确认时只展示支持选择所需的读者目标、关键概念、提纲、推荐路线及理由。等待必要回答时可整理资料、核实事实；沉默或超时不等于确认。

任务明确或相关选择已确认、常规定义补充与润色、保持目的和核心结论的重排删重，以及用户授权自行决定时，直接处理。长文可给简短蓝图，但不能仅因篇幅长增加审批，也不反复确认已有选择。

## 5. 撰写正文

### 段落与解释

- 开篇说明核心问题、回答或方向及必要前提。每段围绕一个主要意思，以完整句子串起对象、动作、原因和结果。
- 解释机制时讲清前提、过程与结果，补足中间推理，不只堆功能点；概念引入按第 2 节执行。
- 抽象机制用准确例子说明，复杂过程优先用贯穿实例，保持对象、名称与条件稳定；注明示意、假设或实际测量。比喻交代对应关系与局限，再回到机制。
- 给出结果或比较后，结合本文问题解释其含义、判断依据和适用范围，不让读者自行补出结论，不擅自更换已约定的评价标准。
- 缺少前提或依据时核实、缩小主张或标明未知；不以过渡句掩盖推理缺口。

### 方法与验证说明

- 先明确方法名称，再说明解决的问题与原理，不能只给分类名、功能或最终结论。
- 按读者背景交代输入、初始状态、中间处理或更新、停止条件与输出。学习或参数估计须解释参数怎样从数据得到，不能只展示最终参数怎样使用。
- 用小例子补齐关键推理，必要时展示一次计算或状态变化。公式与附录补充精度，不承担正文缺失的基础解释。
- 验证说明检查什么、用什么数据、怎样执行和评价；引入对照前解释其规则与输出过程，不只列名称和数字。
- 交代指标、分母、比较差值与结论边界；区分设计要求、当前实现、已执行检查和未验证内容，整体通过不代替逐项依据。多场景保留各自必要的输入、处理及验证条件。

这些要求用于解释已有方法与材料，不规定章节模板，也不要求另行设计实验。

### 中文、名称与术语

- 默认用自然、准确、专业的简体中文。正文采用目标读者能辨认的名称，不用不必要的英文或内部代号增加辨认负担。
- 有稳定译名时优先用中文；原文有检索、辨义或识别价值时首次写“中文名称（原文或缩写）”。无稳定译名时保留通行名称并解释，不发明生硬译名。
- 保留用户指定名称和须精确识别的产品、标准、代码、命令、接口、参数、路径及错误信息，不改写可执行标识符。必要缩写或代号就地说明含义与用途，不要求全部移到附录。
- 同一概念固定称呼，不反复换词、展开缩写或给每个中文名词加英文括注。明确指代，把抽象效果改为具体对象、操作和影响；没有数据支持时不补造百分比或“显著”等强判断。

### 标题与格式

- 文档主标题和各级章节标题采用技术与学术报告风格，以明确对象、范围或研究内容的名词短语为主，不使用问句或口语化提问作标题。问题链用于组织论证，不直接作为目录；去掉问号仍属于提问的表达也须改写。仅在用户明确要求问答体或教学提问时采用问题式标题。
- 同级标题保持抽象层次与表达形式相近，上下级有包含关系。每个标题围绕一个中心任务，不把方法、条件、结果与限制全塞进去，也不为一两句内容另立小节。
- 标题简短且有区分信息，中文章、节标题约 8–16 字仅作参考，不凑字数或损失必要术语。标题与正文名称一致，结论强度符合证据。例：“偏好学习怎样从行为走到可发布策略”应改为“偏好学习与策略生成”，不作为固定目录。
- 段落、列表与表格按文风部分选择。Markdown 保持层级、列表空行、围栏与链接有效，目录和附录按需要设置。
- 逐章用粗体标出少量关键概念、方法或判断，优先在首次或最需辨认的位置强调。后文不反复加粗；普通术语、一般说明和整段正文不加粗，没有重要信息时不为格式凑数。
- MDX 检查 JSX、组件引用及实际渲染；HTML 先审核内容再排版，使用语义化结构、中文语言和字符编码，检查窄屏及阅读顺序。主线所需解释不能藏在默认折叠区，或被卡片与横向跳转打断。

### 图表

涉及业务逻辑或系统架构时，按需读取[图型选择与图文组织](references/system-diagrams.md)。其中规定选图、图文位置、SVG 嵌入、兼容处理及验收。

- 一图回答一个主要问题，抽象层级一致；图前交代必要概念与读法，图后解释判断和限制。名称、关系与正文一致，不设图数配额，简单关系可用文字或表格。
- 依据资料画图，区分现状、拟议与示意；不补造组件或关系，简化不省略影响结论的分支、责任与安全边界。
- Markdown 默认内嵌原始 SVG，不放代码围栏；Mermaid 等制作源图须渲染成 SVG。内联 SVG 标签间不留空行，随文交付所需资源；阅读器不支持时按参考文件处理，不自行替换文档格式。
- 检查完整文档经解析后的实际显示。SVG 的 XML 有效或单独显示正常不能代替此项；不能预览时说明限制，不宣称兼容性已验证。

## 6. 资料、依据与不确定性

调研围绕核心问题综合材料，不按来源顺序拼接摘要。核实影响结论的事实、版本、数字及外部观点，优先一手资料，必要时检索；无法核实时说明范围，不伪装已验证。引用靠近所支撑论点，不编造出处、链接或结果。

区分资料事实、分析推断、假设与待验证内容；来源定义或口径不同先说明差异再比较。调研不支持原假设时，调整结论，不挑选证据维持预设故事。

基于代码写作时核对机制、顺序、分支、状态与异常处理，不凭模块或函数名称推断行为。区分当前实现、设计意图与拟议方案，未确认细节标明待核实；不为叙述顺畅编造行为。

## 7. 审核、修订与复核

### 审核模式

只按目标读者设定审读实际正文与可见附录，不用作者背景、内部工作表或参考资料替正文补解释。写作前初判，完成后重新判断审核方式。

简单说明、措辞排版或少量就地定义由主智能体自行审核。以下任一条件触发子智能体独立审核：用户明确要求；多章相互依赖；概念有多层依赖、涉及跨领域解释，或须综合不同来源证据推导结论；建议影响重要技术选型、架构或实施；改写重构了章节、核心定义或主要论证。不要仅按字数或一个陌生术语触发；用户禁止子智能体时遵从。

触发后读取[独立审核与复核](references/independent-review.md)，固定稿件，以最小上下文交给只读审核者，主智能体统一修订。默认一名全文审核者，专项检查不能替代全文审读；正常触发无需追加审批。工具不可用时完成自行审核并说明限制；若独立审核是用户指定前提，只能交付未满足该前提的可审阅稿。

### 文档受众对象视角与对抗性审核

有明确的判断、选择、评审、验证、使用或实施目标，或用户明确要求受众视角审读时，在通用审核中增加针对性对抗检查。基础原理解释、简单说明和纯措辞排版任务仍以理解与准确性为主，不为制造对抗而附加无关的决策要求。详细角色库、攻击模式和审核输出规则见[文档受众对象对抗性审核](references/audience-adversarial-review.md)，仅在适用时读取。

- **选择角色**：按文档用途、已确认的实际受众与预期任务，选一名主要角色，确有不同的关键责任时再选一至两名辅助角色。基础角色有决策审批者、业务需求者、技术评审者、工程实施者、验证评价者、运行保障与风险审查者；研究型文档可另选研究同行或证据质询者。角色表示审读职责，可重叠，不是固定职级，也不要求全部覆盖。未知身份只能作为模拟审读假设。
- **明确任务**：先确定各角色读完必须回答的少数关键问题，以及会使其无法完成判断或行动的证据缺口、条件缺失和重大风险。主要角色的任务决定审核优先级，不能把辅助角色偏好变成新写作要求。
- **独立质询**：以已交付给受众的正文、图表及可见附录为检查对象，从前提、证据、反例或边界、替代方案、判断与行动可用性五方面质询重要结论。记录具体位置或明确缺失项，并说明该缺陷如何影响特定受众的任务；不得用作者内部推理为正文补证，不得凭空断言缺陷或要求每个角色提出固定数量的问题。
- **统一处理**：将问题并入通用审核清单，由主智能体分类、去重、判定采纳与否并修订。优先解决影响核心判断、决策、验证或执行的实质缺陷；资料不足时核实、限定结论或标明待验证，不编造证据、预算、测量值或故障。修订后复核受影响论证及受众任务；不机械增加章节或延长审核轮数。

独立审核已触发时，尽量在同一名只读审核者的全文审读中纳入角色质询；仅当任务确实需要不同领域的独立判断且工具允许时增加专项审读，专项意见不能代替全文审读。独立审核未触发时，主智能体按相同规则自行检查。

### 检查与修订

以下检查是同一篇文档的审核维度，不要求各自启动一次流程。检查全文或已约定范围；修改结构、概念或结论后重新核对受影响部分。

| 维度 | 检查重点 |
| --- | --- |
| 任务与主线 | 核心问题是否回答；各节是否有作用，能否连续还原论证 |
| 文档受众对象与任务可用性 | 是否回答主要受众完成判断或行动必须关心的问题；核心结论与依据、条件、取舍、风险及限制是否匹配；对纯解释型文档不附加无关的决策要求 |
| 概念与关系 | 首次接触时是否能理解；是否依赖后文；整体对象与分类维度关系是否清楚，标题图表有无提前使用 |
| 语言与名称 | 中文是否自然；名称是否适合读者；缩写代号与指代是否清楚；简化有无损失条件和推理 |
| 方法与结果 | 原理与形成过程是否可追踪；比较对象是否解释；结果含义、判断依据、分母与范围是否清楚 |
| 准确性 | 事实、推断、假设及实现状态有无混淆；依据、口径和限定是否齐全 |
| 结构与篇幅 | 主标题及各级标题是否符合报告风格、有无残留问题式表达；标题是否准确分层；表达形式是否合用途；抽象内容、重复与碎片化是否妨碍理解 |
| 图表与格式 | 图文是否对应，位置与阅读顺序是否合理；分支、资源、解析、实际显示及链接是否检查 |

用户指出实例后，识别其表达或结构问题，检查授权范围内的其他同类位置，包括标题、表格、图中文字与附录；不把举例当作完整清单，也不扩大到无关工件。

对问题记录位置、读者为何卡住及修法；逐项判断采纳、部分采纳、未采纳或待核实，并给理由。优先解决关键和重要问题，表达建议按用途处理。结构与推理缺口须补解释、重排或修正论证，不只加过渡词；修改后复核前后影响。改变已确认方向时按第 4 节处理，启用独立审核后的复核方式按参考文件执行。

### 完成标准

最终进行三项验收，第三项按文档用途适用：

1. **顺序阅读**：不回跳、不查外部资料也能理解核心论证的必要概念；前置知识只限开篇明确约定的范围。
2. **章节串联**：串起各节问题与结论，能还原连续推理，而不是孤立主题集合。
3. **受众任务达成**：主要文档受众对象能够仅依据正文与约定的可见材料，获得其预期理解或完成相应判断、选择、验证、使用、执行。对需要作出实质判断的文档，必须交代支撑结论的必要依据、条件及重要限制；不强制说明型文档增加成本、审批或实施计划。

关键问题指阻断核心理解、使核心结论不成立，或使主要受众可能作出严重错误判断或行动的问题；重要问题指影响局部理解、必要判断或可操作性的问题。已确认的这两类问题均须修复并复核。无法解决时明确未满足项与交付状态；事实依据不足须查证、缩小主张或保留明确限制。表达偏好不作为无限改写的理由，完成后停止，不追求固定轮数。

所有修订均须复核实际交付版本，核心内容再次变化时重查受影响范围。自行或独立审核、结构校验与主观评分都不能保证零错误，不得把未执行的检查写成已完成。

## 8. 交付

交付经修订的正文或指定文件，简短说明重要假设、实质修改、实际检查和剩余限制；适用受众对抗性审核时，可概述主要角色和已处理的关键问题，不附内部工作表、完整审核对话或主观评分。用户只要初稿时说明未完成完整审核；只审核时列具体位置、原因与修法，不覆盖原文。

含图文档说明图表解释的问题和实际显示检查范围，随文交付全部引用资源。启用独立审核时说明覆盖范围与问题处理情况，未检索、未渲染或未全文审读的部分如实说明。
