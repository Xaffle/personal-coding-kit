# 图型选择与图文组织

本指南用于中文技术文档中的业务逻辑与系统架构说明。先确定读者此刻想理解什么，再选能直接呈现该关系的图。图型是表达工具，不要求每篇文档把所有类型画一遍。

## 按读者问题选图

| 读者的问题 | 适合的图 | 应呈现的内容与适用场景 | 注意区别 |
| --- | --- | --- | --- |
| 系统负责什么，与谁交互？ | 业务或系统上下文图；C4 上下文图（C1） | 系统边界、用户、外部系统与交互内容；适合开篇建立全局认识 | 不展开内部模块，不把外部交互误画成内部处理 |
| 谁可以使用哪些能力？ | 用例图（UML Use Case） | 参与者、系统能力及能力边界；适合说明角色与功能范围 | 不表示执行顺序，也不能单凭用例图推断权限规则 |
| 谁在何种条件下完成什么步骤？ | 业务流程图（BPMN），按责任划分泳道 | 活动、角色、触发事件、审批、分支和异常；适合跨角色业务流转 | 区分人工操作和自动动作；泳道是责任分区，可配合 BPMN 或活动图使用 |
| 系统内部如何执行一个过程？ | 活动图（UML Activity） | 内部步骤、条件、并行与汇合；适合算法外围处理或软件执行逻辑 | 多角色业务协作优先考虑 BPMN 或泳道图，不把所有流程都画成调用时序 |
| 业务对象是什么，彼此有什么约束？ | 领域模型图（DDD） | 领域对象、聚合、值对象与业务关系；适合建立业务概念 | 面向业务语义，不默认等同于数据库表；聚合等术语须就地解释 |
| 数据如何存储，实体之间如何关联？ | 实体关系图（ER 图） | 实体、必要属性、标识及一对多、多对多等基数约束；适合说明数据结构 | 区分概念数据模型与实际表结构，不凭业务关系推断已实现的外键 |
| 一个对象可以处于哪些状态，何时改变？ | 状态机图 | 生命周期状态、事件、转换条件及终止状态；适合审批对象、任务或策略版本 | 状态是对象处境，活动是执行动作；只画有依据的转换与驳回、撤销、回退路径 |
| 系统由哪些应用、服务或存储组成？ | C4 容器图（C2） | 可运行的应用或服务、数据存储、职责与关系；适合系统内部总览 | C4 的“容器”是架构单元，不专指 Docker 容器；此图不替代物理部署图 |
| 一个应用内部如何分工，模块依赖什么？ | 组件图或模块图；C4 组件图（C3） | 组件职责、接口与依赖；适合解释某个应用内部划分 | 与 C2 总览分开，静态依赖不表示每次请求都按此顺序运行 |
| 一次具体场景中，谁先调用谁？ | 时序图（UML Sequence） | 参与对象、消息顺序、必要入参和返回、同步或异步、超时与回调；适合请求链路与异常排查 | 明确场景及前提，按需要展示关键异常；时序图不替代全业务流程图 |
| 服务运行在哪里，如何连通？ | 部署图（UML Deployment） | 设备或服务器、进程或容器、存储、网络连接及部署边界 | 逻辑模块不等于部署节点；区分规划部署与已核实部署 |
| 数据从哪来，经过什么处理，流向哪里？ | 数据流图（DFD） | 数据来源、处理、存储与输出；适合采集、分析、报表等数据链路 | 箭头注明数据内容；数据流不自动表示控制流或时间顺序 |
| 系统分成哪些层，各层负责什么？ | 架构分层图 | 层的职责、允许依赖方向及跨层约束；适合快速理解技术分工 | 不把概念分层当作物理部署，不因纵向排列就暗示每次调用经过所有层 |
| 复杂业务中，哪些事件由什么命令触发？ | 事件风暴图 | 业务事件、命令、参与角色、聚合与待澄清规则；适合业务与技术人员共同梳理领域 | 区分探索记录与确认后的模型；讨论中的关联不能直接当作运行时调用 |
| 必须理解实现中的类或代码关系吗？ | C4 代码图（第四层），可用类图等表达 | 类、接口及实现关系；用于代码结构确实影响论证的局部 | 通常不需要展开到这一层；C4 模型名称与第四层代码图的含义要写清 |

使用 BPMN、UML 或其他正式记法时保持符号含义一致。只采用简化框线表达时，标为“业务流程示意”或“模块示意”，不要把普通框线图宣称为严格符合某种建模规范的图。

比较方案、规则、权限或指标时，表格通常更直接。比较项采用同一口径；数值图表须注明数据来源、单位和统计条件，不用示意数据支持实际效果判断。

## 把图放进论述

对从零解释一套系统的长文，可按以下理解关系安排图：先看上下文和边界，再看业务流程与领域对象；涉及对象生命周期时给状态图；介绍内部划分时给 C2 总览或组件图；进入具体场景时给时序图；说明存储设计时再给 ER 图。这是可调整的阅读路线，不是固定目录。部署和数据流图放在读者开始关心运行位置或数据去向的段落附近。

每张图都应有明确的正文落点。例如，说明审批流程时，先交代申请人和审批者的职责，再给泳道图，随后解释驳回和重新提交如何发生。不要在尚未解释角色时让图承担全部定义，也不要在讨论审批规则的两句话中间插入部署图。

- 图前写清对象、范围和必要读法；横轴、泳道、箭头或线型含义容易误解时，给简短图例。分支、状态或类别不能只靠颜色区分，应同时使用文字、线型或形状。
- 图题应能定位内容，例如“图 3：候选策略的审批状态与转换条件”。图后解释本节要得出的判断、关键分支及省略范围，不逐个复述图中的标签。
- 跨图使用同一对象名称。总览中的模块展开成局部图时，保留名称和边界对应；现状与拟议方案并列时显式标明。
- 将密集大图拆为总览与局部图，各自靠近相关段落。图的可读性不能以正文回跳、持续横向滚动或极小字号为代价。

## Markdown 中嵌入 SVG

默认把 SVG 标记直接放入 Markdown 正文，前后留空行，不放在列表缩进或代码围栏中。SVG 应自包含，不依赖远程图片、字体、脚本或外部样式。用 `viewBox` 保持缩放比例，使用常见中文字体回退；同一文档中各图的元素标识符应唯一，避免箭头标记或标签引用冲突。

从 `<svg>` 起始标签到 `</svg>` 结束标签之间不留空行，包括只含空格或制表符的行。部分 Markdown 解析器遇到空行会结束 SVG 所在的 HTML 块；后续有四个空格缩进的元素可能被识别成代码块，造成图形缺失或标签以代码显示。这样的 SVG 单独打开仍可能正常，XML 校验也可能通过。元素可以逐行书写并保留缩进，需要分组时使用不带空行的 XML 注释。

下例只演示正文与内联 SVG 的位置关系。代码围栏用于展示写法，生成实际报告时去掉最外层围栏，并用符合业务事实的图形替换示例。

````markdown
本节解释记录如何进入校验步骤。下图的箭头表示记录的传递方向。

  <title id="fig1-title">图 1：记录进入校验步骤</title>
  <desc id="fig1-desc">记录由采集模块传给校验模块。这是流程片段示意，未展示异常分支。</desc>
  <defs>
    <marker id="fig1-arrow" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="7" markerHeight="7" orient="auto-start-reverse">
      <path d="M 0 0 L 10 5 L 0 10 Z" fill="#334155"/>
    </marker>
  </defs>
  <rect x="30" y="30" width="180" height="70" rx="6" fill="#f1f5f9" stroke="#334155"/>
  <rect x="390" y="30" width="180" height="70" rx="6" fill="#f1f5f9" stroke="#334155"/>
  <path d="M 210 65 H 380" fill="none" stroke="#334155" stroke-width="2" marker-end="url(#fig1-arrow)"/>
  <g fill="#0f172a" font-family="sans-serif" font-size="20" text-anchor="middle">
    <text x="120" y="73">采集模块</text>

该片段说明校验的输入来自采集结果；它未规定校验失败后的处理方式。异常路径应在讨论校验规则时另行说明。
````

如果目标阅读器过滤原始内联 SVG，但支持以图片方式加载本地 SVG，可把同一 SVG 保存为随文资源，在原位置使用 `![图题与简短说明](assets/fig-01.svg)` 嵌入，并一并交付资源目录。此时文档包含本地引用，不再是单文件自包含；需要单文件交付时仍保留内联 SVG，并说明该阅读器的显示限制。不得只放“下载 SVG”的链接或把图移到附件中，让正文失去图示。

若目标阅读器两种方式都不支持，保留原要求的 Markdown 和 SVG，说明图在该阅读器中不能显示；需要变更交付格式时遵循用户要求，不自行用 PNG 或 HTML 替换。无法使用目标阅读器时，也应说明兼容性尚未验证。

## 图表验收

审核图表时，同时查看正文、实际 SVG 和阅读器显示结果：

- 内容：图型是否适合本节问题；节点、箭头、基数、状态和责任是否有依据；简化是否省略了影响结论的条件；图与正文有无矛盾。
- 阅读顺序：读图所需概念是否已经解释；图是否紧邻相关论述；图前导读和图后解释是否足以让读者继续顺读。
- 文件结构：SVG 的 XML 是否有效，标识符和引用是否对应，是否依赖未交付的资源；本地引用是否能随文档移动。
- Markdown 解析：以完整文档为输入，确认内联 SVG 没有被空行拆开，元素没有落入代码块或被转义成文字。优先用目标阅读器检查；无法访问时，用可用的 Markdown 解析器生成 HTML，再在浏览器中检查。必要时对照源图与解析后图形的文字、矩形、路径等元素，定位缺失内容。
- 显示：中文是否缺字，标签是否越界或重叠，连线是否遮挡，箭头是否可辨；在目标页面宽度及缩放后是否仍能读清，是否被阅读器过滤。

语法检查只能验证文件结构。直接把 SVG 放进浏览器，也不能验证 Markdown 的解析与过滤行为。检查应经过“完整 Markdown → 阅读器解析 → 页面显示”这条路径；使用其他解析器代替目标阅读器时，说明实际验证的范围，不能据此宣称目标阅读器兼容性已确认。发现显示问题应修复、拆图或按上面的兼容规则处理，再检查实际交付版本。
