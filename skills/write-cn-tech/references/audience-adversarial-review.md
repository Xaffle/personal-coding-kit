# 文档受众对象对抗性审核

本参考文件供 `write-cn-tech` 的第 7 节按需读取，服务于**文档受众对象视角与对抗性审核**。它是通用审核的专项维度，不代替事实核实、逻辑审核、独立全文审核与修订复核，也不要求文档天然用于汇报。除非用户指定，不向交付正文附加审核角色、内部清单或评分。

## 1. 目标、适用边界与输入

目标是验证：**实际或合理设定的文档受众对象，在不借助作者脑中信息的情况下，能否凭当前文档完成它承诺支持的理解、判断、选择、评审、验证、使用或执行。** 对抗的对象是结论、前提、证据与任务适配性，不是作者本人或写作风格。

- **适用**：方案选择、架构/设计评审、技术调研、研究结论、效果验证、需求分析、工程交付、操作规程、上线/运行评估等有明确受众任务的文档；用户明确要求时也可应用于其他文档。
- **轻量或不启用**：只需解释原理或作少量措辞修改，且没有额外判断/行动需求时，完成常规读者理解与准确性审核即可；不为了角色覆盖强加预算、ROI、实施计划、验收或审批段落。
- **必要输入**：完整的待审文档（或已约定片段）；已知受众与任务；用户指定的范围、评价标准和不可变更约束；如有，正文中实际呈现的引用或可见附录。
- **未知信息**：若受众身份不明，依据文档用途选择“模拟审读角色”，标记为假设；不能将模拟审查意见当作真实受众要求。若不同角色会实质改变技术路线或篇章深度，遵循主 Skill 第 4 节处理必要确认。
- **证据边界**：审阅文档是否自足时只能依赖受众能看到的内容；外部来源可用于核实事实，但不能替正文补上本应呈现的关键论证。不得推断未提供的组织策略、预算、法规义务、性能指标或项目承诺。

## 2. 角色选择

### 选择原则

1. 从用户要求和文档目标反推**主要审读任务**，据此选择**一名主要角色**；角色是职责视角，不是职位或汇报层级。
2. 只有在存在独立且重要的判断责任时，才增加**一至两名辅助角色**；同一人可以同时承担多种职责，不必为每个视角启动独立模型。
3. 重要结论的安全与合规风险应由适当专业角色检查，不能仅因一般角色上限而忽略必要专项审核。需要专门法规结论时仍必须有相应可靠依据。
4. 角色关注点之间存在冲突时，以**真实受众任务、用户约束、证据事实与文档范围**排序；保留必要限制，不拼接所有建议使正文臃肿。
5. 如果没有足够证据推断受众任务，优先遵守用户指定读者和用途，使用最保守、最贴近文档的模拟角色；不要捏造角色立场。

### 七种可选角色及角色卡

角色卡里的“否决点”表示会使相关判断无法成立的**可检查问题**，不代表审核员预设报告已经失败。

#### ① 决策审批者（决策可用性）

- **典型任务**：评估是否批准、采用、继续、投入或放弃一个技术选择；不预设该文档一定用于审批。
- **最关心**：问题的实际重要性、可选方案、预期效果、必要资源、取舍、风险、决策条件。
- **质询示例**：为什么现在要做？不做的代价是什么？为何推荐方案比可行替代方案更合适？收益是否足以支持声称的投入？哪些未知会改变建议？我到底需要决定什么？
- **关键否决点**：建议需要决策，但没有给出决定所必需的目标、比较依据、前提或重大风险；把技术可行直接等同于值得投入。
- **不要强加**：给非审批、非选型文档补造成本、预算或商业回报指标。

#### ② 业务需求者（需求匹配性）

- **典型任务**：判断技术方案是否满足真实业务目标与典型使用场景。
- **最关心**：需求对应关系、使用流程、业务效果、边界场景、用户负担、可接受的验收口径。
- **质询示例**：解决的真是需要解决的问题吗？技术指标如何影响实际使用效果？哪些业务场景未覆盖？新增了什么操作或依赖？怎样判断需求得到满足？
- **关键否决点**：所展示技术优势无法对应既定需求；把代理指标改善当作已经证明的业务收益。
- **不要强加**：在纯机制解释中要求完整的业务模型或产品路线图。

#### ③ 技术评审者（技术可信性）

- **典型任务**：判断原理、设计假设、接口边界和方案取舍在已知条件下是否成立。
- **最关心**：关键机制、隐含假设、约束、反例、替代方案、技术债、可验证证据。
- **质询示例**：这个机制为何有效？最小反例是什么？在哪些输入或负载下失效？是否忽略一致性、兼容性或依赖边界？为何不使用更简单方案？结论依赖哪些尚未证明的条件？
- **关键否决点**：核心推理不成立；重要约束与设计矛盾；推荐结论超过已给证据的支持范围。
- **不要强加**：与文档问题无关的技术细节、无依据的假设性缺陷。

#### ④ 工程实施者（工程可实施性）

- **典型任务**：根据设计/规程执行、集成、迁移、配置、部署或交付。
- **最关心**：前置条件、依赖、责任边界、关键步骤、异常处理、迁移/回滚、完成判定。
- **质询示例**：能否仅凭该文档确定从现状到目标的路径？环境和接口要求在哪里？执行失败如何处理？哪些步骤不能交换顺序？交付完成如何核对？
- **关键否决点**：文档宣称可供实施，却缺失阻止安全执行的前提、关键步骤或必要检查。
- **不要强加**：让原理介绍文档承担工程实施手册的职责。

#### ⑤ 验证评价者（结果可验证性）

- **典型任务**：判断设计要求、试验结果或性能收益是否获得足够的证据支持。
- **最关心**：评价指标、样本/环境、基线和对照、测试覆盖、误差、复现方法、结论强度。
- **质询示例**：改善的指标究竟是什么？分母、口径和基线是什么？测试覆盖关键场景吗？是否将相关性写成因果？结论适用范围比验证范围更大吗？
- **关键否决点**：关键指标无定义或证据不足；无法区分“设计要求”“已执行验证”“尚未验证”；结果外推无依据。
- **不要强加**：对未承诺验证的解释型材料要求补做新实验。

#### ⑥ 运行保障与风险审查者（风险和运行可控性）

- **典型任务**：判断方案投入实际使用后的故障、安全、恢复、维护与责任是否可控。
- **最关心**：故障模式、失效影响、监测告警、降级恢复、回滚、安全边界、持续维护代价。
- **质询示例**：关键故障或恶意输入下会怎样？如何发现和恢复？是否引入新的单点依赖？安全和权限边界是否说明？问题发生时谁负责处理？
- **关键否决点**：已知重要风险未交代，或文档声称“安全/可靠/可上线”但缺乏对应依据与边界。
- **不要强加**：未经验证就断言存在漏洞、故障或违法；也不把所有安全领域都纳入每篇文档。

#### ⑦ 研究同行或证据质询者（研究结论可信性，可选）

- **典型任务**：对研究、算法、技术调研或实验性结论进行独立证据质询。
- **最关心**：研究问题、方法合理性、样本与数据、对照公平性、假设、替代解释、可复现性、推广边界。
- **质询示例**：方法为何适用于这个问题？数据是否代表目标场景？排除了哪些替代解释？是否挑选了有利结果？实验差异能否支撑因果结论？换场景后结论仍成立吗？
- **关键否决点**：核心发现缺乏支撑，比较前提不一致，或者推断与证据强度明显不匹配。
- **不要强加**：把所有技术说明改写成论文格式或要求并不存在的实验数据。

当网络安全、隐私、强制性合规或安全关键领域本身构成文档的主要判断目标时，可将相关专业审查作为独立专项职责，但不得假设某个具体法定要求自动适用。

### 按文档任务选角（启发式而非硬映射）

| 文档主要任务 | 可能的主要角色 | 何时增加辅助角色 |
| --- | --- | --- |
| 解释原理、技术概念 | 一般目标读者；必要时技术评审者 | 仅在文档提出实质技术结论时 |
| 技术选型、架构决策 | 技术评审者或决策审批者 | 有明确业务收益、工程实施或安全约束时 |
| 需求分析、解决方案 | 业务需求者 | 同时承诺选型、验证或落地时 |
| 设计/实施/迁移说明 | 工程实施者 | 技术风险或运维条件关键时 |
| 测试、性能、效果验证 | 验证评价者 | 技术机理或业务效果是核心论点时 |
| 运行方案、风险评估 | 运行保障与风险审查者 | 涉及重要设计权衡或验收依据时 |
| 研究报告、算法评估 | 研究同行或证据质询者 | 结果需要应用决策或工程转化时 |

## 3. 五种对抗性质询方法

优先挑战影响受众主要任务的**关键结论**，而不是逐段生成泛化意见。五种方法视需要组合，不能机械覆盖或强迫发现问题。

| 模式 | 核心问题 | 典型发现 |
| --- | --- | --- |
| **前提攻击** | 哪个必要假设被省略、未验证或与已有材料矛盾？若它不成立，结论是否变化？ | 默认负载、数据条件、外部依赖与实际场景不一致 |
| **证据攻击** | 证据的定义、来源、口径、对照、推理链能否支持结论强度？ | 无基线、指标分母不明、把计划当结果 |
| **反例与边界攻击** | 哪个合理、与任务相关的例外情形会削弱结论？文档是否说明边界？ | 只检查正常路径，忽略高风险边界 |
| **替代方案攻击** | 当文档要求选择方案时，是否遗漏具有现实意义的替代方案或重要比较标准？ | 只证明方案可行，没解释为什么应选它 |
| **判断与行动攻击** | 假设正文全部正确，受众仍缺什么信息才能决定、验收或执行？ | 缺少实施前提、验收条件、风险处理或决策阈值 |

操作约束：

- “可能发生”不是“已经发生”。提出反例时标记其为**待核实边界**，并说明它为何与文档目标相关；不能把构造的反例写成事实。
- 文档没有提供某项信息，不等于该事实不存在。区分**正文信息缺失**与**外部事实尚未验证**。
- 若受众明确只需概念理解，不得用“缺少 ROI/预算/上线计划”作为缺陷。
- 若核心任务是对比或批准方案，不能以“文字已经解释清楚”为由忽略关键取舍、成本、证据或不确定性。
- 主体论证已经足以完成任务时，可以得出“未发现相关严重缺陷”，不要求每类攻击都产生意见。

## 4. 审读执行步骤

1. **固定稿件与目标**：记录范围、文档类型、用户指定读者、已确认/模拟角色、各角色的一句话任务，以及不应越界的要求。只读审核员不直接改动稿件。
2. **提取核心承诺**：用简短语句写出文档声称解决的问题、重要结论、预期使用方式及证据位置；判断这些承诺是否仅是解释、还是已上升为选型、验证或执行。
3. **列出关键质询**：每个角色仅保留影响其任务的少数问题，先检查是否已被正文完整回答；已充分回答的，不列为缺陷。
4. **构建反证尝试**：对重要结论优先使用前提、证据、反例、替代方案、判断与行动五类方法。确定的是**文档中可定位的不足**，不是未经查证的外部事实。
5. **形成问题单**：对每个问题明确“角色→受众任务→质询→证据位置/缺失项→影响→修法”。合并不同角色指出的同一根本缺陷。
6. **主智能体裁决与修订**：区分采纳、部分采纳、不采纳、待核实。优先补证、重构推理、调整结论强度或声明限制；不为消除异议编造数据，也不自动采纳所有角色偏好。
7. **定向复核与停止**：对关键和重要问题重新检查修订稿；修改结论或结构后复核受影响上下文。受众任务已有充分支持、无未处理关键/重要问题，或无法补证的限制已明确后停止；不追求固定轮数。

### 问题分级

- **关键**：核心结论无法成立、主要受众无法完成必要判断/行动，或者重要信息缺失可能导致严重错误选择或高风险执行。
- **重要**：明显妨碍局部判断、关键条件理解、验证或实施，但不必然推翻整体结论。
- **一般**：改善检索效率、表达体验或次要解释，不改变重要判断。

严重程度要说明影响链条；不能仅凭审查角色的重要性判为“关键”。具体合规或安全风险的严重性必须基于文档与已验证要求判断。

### 单项问题的最小输出格式

| 字段 | 填写要求 |
| --- | --- |
| ID / 严重程度 | 同一根本缺陷只计一项；关键/重要/一般 |
| 文档受众对象角色 | 主要或辅助，必要时标注模拟假设 |
| 任务与对抗性质疑 | 该角色究竟无法判断/执行什么，具体追问什么 |
| 证据定位 | 章节、段落、表格或短引用；缺失项需说明已检查的范围 |
| 影响与事实状态 | 影响何种判断；明确事实缺口、推理缺口或待核实假设 |
| 最小修订建议 | 补充必要依据/限制，调整结论，或说明应如何验证；不代写不存在的数据 |
| 处理状态 | 采纳、部分采纳、不采纳、待核实，及理由；复核结果 |

若用户**只要求审核**：保留原文，只交付具体问题与修法。若用户要求**写作或修订**：问题单原则上作为内部工作表，不应替代实际修订后的文档；对外简要说明实质修改与未解决限制即可。

## 5. 独立审核者任务指令（模板）

独立审核已经根据主 Skill 触发时，将这一专项内容**合并进入既有全文审读任务**；默认不另开一组角色智能体。以下模板只包含本专项约束，实际使用时应同时执行通用全文审读和已有独立审核规则。

> 你是只读技术文档审核者。请独立审阅所给固定稿件的实际正文及可见附录，不依赖作者的内部解释或未提供资料填补正文。本文档的已确认受众为：{如有则填写}；为审读设定的模拟角色为：{如有则填写}；主要受众任务为：{任务}；辅助角色及任务为：{必要时填写}。遵守已给的文档范围与不可变更要求。
>
> 先识别文档承诺支持的核心判断和重要结论。用前提、证据、合理反例或适用边界、必要的替代方案比较，以及受众判断与行动可用性五种方法，寻找实质缺陷。仅报告已通过实际正文定位且能说明影响的问题，不要求每个角色都有意见；不要编造风险、业务要求、实验结果或缺失的外部事实。根据关键、重要、一般分级，给出位置、质疑、影响与可执行修订方向；不同角色的重复问题合并。不要改写正文，不要因文档类型不相关而强加预算、审批或实施计划。找不到实质问题时如实说明。

独立审核工具无法使用时，主智能体按相同检查点自行执行，必须如实说明审核方式；若用户明确要求独立审核为交付前提，不得宣称已完成。

## 6. 示例：区分实质质询与无效建议

**待审结论（假设性示例）**：“采用新缓存架构后，系统整体性能提升了 30%，因此建议全面推广。”

| 角色 | 有价值的质询 | 需要查证或修订的点 |
| --- | --- | --- |
| 验证评价者 | “30%指吞吐量、延迟还是其他指标？对照与测试条件是什么？” | 指标定义、基线、环境、统计口径及结论边界 |
| 技术评审者 | “缓存命中率、读写比例与一致性约束如何影响该收益？” | 机制、成立条件、必要边界，不预设已经存在一致性问题 |
| 决策审批者 | “证据是否足以从一次测试推出‘全面推广’？是否有分阶段验证的条件？” | 推荐强度、推广条件、必要的替代路径与风险信息 |

无效或过度的建议包括：“既然是技术文档，就必须增加商业回报章节”“多写三条风险”“为了对抗而断言架构存在单点故障”。应删去不服务于已确认受众任务的要求。若资料不能支撑“全面推广”，应先限制结论或明确待验证条件，而不是编造试点效果。

## 7. 与主 Skill 的兼容要求

- 第 1 节负责识别读者背景、实际受众任务与角色依据；本文件只指导专项检查，不替代读者理解路线。
- 第 3 节仍以连续论证为优先；补充受众所需信息应优先就近整合，而不是增加机械的“管理者关切/专家关切”章节。
- 第 4 节继续控制哪些实质方向变化需要向用户确认；审核角色不得擅自更改已约定范围。
- 第 6 节继续核实事实及不确定性；对抗性检查不授权虚构证据。
- 第 7 节以统一问题清单、主智能体修订、定向复核收束；本文件不增加默认审核轮数，不替代 `references/independent-review.md`。
- 第 8 节按用户请求交付成稿或具体审核意见；不默认附角色卡、内部质询对话或评分。
